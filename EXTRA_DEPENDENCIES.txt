-----------------------------------------------------------
7a. YOU SHOULD NOT NEED TO RESUME ANY MORE
-----------------------------------------------------------
A run used to abort on the FIRST series where the LLM failed. That is what forced
the ANP resume, and the resume is what silently disabled the pooled meta-model for
the last 17 rows (7b below). Fixed at the source:

  * transport errors are retried 4x and empty replies 2x, without spending an
    iteration - most gpt-oss glitches never surface at all;
  * `max_llm_failures` (default 5) is a BUDGET, not a hair trigger. One flaky
    series costs one row, marked in the log and in the CSV. A genuinely broken
    server still stops the run within a few series, with the reason.

So: run the whole dataset in one call and let the budget absorb the glitches.
  --max-llm-failures 5     default; raise it if a dataset is unusually flaky
  --allow-baseline-fallback  never abort (every failed row becomes a baseline)


-----------------------------------------------------------
7b. RESUMING A RUN - READ THIS BEFORE USING --indices
-----------------------------------------------------------
The pooled meta-model trains on the series of THE CALL, not of the dataset. A
resume chunk smaller than `pooled_meta_model_min_series` (default 20) therefore
trains nothing, and `weights_pooled_meta_model` is withheld for every series in
that chunk - a different architecture for part of the CSV.

This already happened: the ANP v4 run was finished with indices 165-181 (17
series), and those 17 rows silently had the tool withheld. The run now prints

  WARNING      : this call covers 17 series but pooled_meta_model_min_series=20 ...

at startup and records it in every affected row's warnings. Prefer running a whole
dataset in one call; if you must resume in a small chunk, lower the minimum so the
architecture stays identical across series.


-----------------------------------------------------------
7c. gpt-oss ON OLLAMA - KNOWN ISSUES
-----------------------------------------------------------
Two failure modes on real runs, both from gpt-oss's harmony format:

  90 EMPTY replies (ANP v4, 182 series) - the model spends its budget in the
     reasoning channel and emits nothing in the final one.
  "error parsing tool call: raw='We will call ...'" - Ollama's own template tries
     to JSON-parse prose written into gpt-oss's tool-call channel, and returns an
     error instead of the text. ollama/ollama#11781, #11800.

IMPORTANT: reasoning is ALREADY ON in every run so far. gpt-oss's own default is
to reason, and we pass nothing, so "turning reasoning on" is not an available
improvement - it is the status quo. The knob moves in these directions instead:

  --reasoning low     keep reasoning, cap its budget. The empty replies are the
                      model reasoning and then having nothing left for the answer,
                      so this is the targeted fix for them.
  --reasoning high    more deliberation per turn. Untested here; plausible for a
                      task that is mostly judgement, but it makes the empty-reply
                      failure MORE likely, not less.
  --reasoning off     no reasoning at all. Also removes the harmony tool-call
                      channel behind the "error parsing tool call" errors.
  (unset)             the model default = what v1-v4 used. Keep it for comparability.

Mitigations, in order:
  1. Upgrade Ollama on the server - both issues have had fixes land upstream.
  2. A/B `--reasoning low`. Treat it as a deliberate arm; it enters fingerprint().
  3. If it persists, A/B the combinator model (`--combinator qwen3:14b`). The
     three-line text contract is model-agnostic on purpose.

Do NOT use format="json" as a workaround: on gpt-oss the response comes back empty
every time (ollama/ollama#11867). The loop already retries empty replies (2x) and
transient transport errors (4x) without charging the iteration budget.


-----------------------------------------------------------
8. WHEN THE AGENT FAILS
-----------------------------------------------------------
By default a run ABORTS when the configured agent does not answer, because a run
that silently degrades to the deterministic baseline still logs `ok` and answers a
different question. The message names the model, the URL and what to check.

  use_llm=False                   deliberately run the deterministic arm
  allow_baseline_fallback=True    keep going and fall back per series
  --quiet-agent                   stop printing Thought/Action/Observation per turn

Redirect stderr as well, or the traceback is lost:

  nohup python3 run_tsf_orchestrator.py > logs/v1_proposta.log 2>&1 &
